1. Executive summary and goals
Build a production-minded, multi-tenant School Management SaaS platform for multiple independent schools. It should manage academic, administrative, communication and financial operations while keeping each school's data isolated. The initial architecture should be a modular monolith: one Next.js application, one Supabase Database database, clearly separated domain modules, and background jobs for work that should not run inside a web request.
Product goals
* Give each school its own secure workspace, academic calendar, grading configuration, classes, branding and fee settings.
* Provide role-specific experiences for platform operators, school leadership, teachers, finance staff, parents/guardians and students.
* Reduce manual work in admissions, attendance, grading, report cards, fee collection and communication.
* Support SaaS plans, school onboarding, usage limits, audit trails, backups and a path to scale.
MVP non-goals
* Do not begin with microservices, Kubernetes or unnecessary infrastructure.
* Do not implement every optional module before core student, academic and finance workflows are dependable.
* Do not treat hidden UI buttons or payment redirects as security controls.
* Do not claim legal compliance without qualified review.

4. Functional requirements
4.1 Tenant onboarding and school settings
* Create a tenant with unique slug/code, contacts, timezone, locale, currency, logo and branding.
* Track pending, trial, active, suspended and closed states; enforce access rules for each state.
* Configure academic years, terms, grading scales, attendance rules, fee categories and receipt numbering.
* Require a reason and audit entry for platform suspension/reactivation.
4.2 Admissions and student information
* Capture applications, guardians, documents and admission status.
* Convert accepted applications to student/enrollment records transactionally without duplicate conversion.
* Track student IDs, status, enrollment history, class placement, emergency contacts and documents.
* Use transfer/withdrawal/archive states without deleting academic or financial history.
4.3 Staff and access
* Create staff profiles and explicit school memberships.
* Assign roles/permissions; revoke access and invalidate sessions when needed.
* Separate employment information from login identity and authorization claims.
4.4 Classes, subjects and timetable
* Manage class groups, streams, subjects, teaching assignments, rooms and periods.
* Detect schedule conflicts and restrict teachers to assigned classes unless separately authorized.
4.5 Attendance
* Record attendance by class/date/session with present, absent, late and excused statuses.
* Prevent duplicate records with constraints and idempotent save logic.
* Require permission and a reason for corrections; preserve before/after audit data.
* Provide summaries and optional guardian notifications.
4.6 Assessments and report cards
* Configure assessment categories, weights, grading bands, terms and publication rules.
* Validate score ranges and define missing, exempt and absent score handling.
* Support draft, submitted, approved and published states.
* Generate downloadable/printable report cards with publication history.
4.7 Fees and payments
* Create fee schedules, invoices, line items, balances, discounts and waivers.
* Track payment attempts, allocations, receipts, reversals, refunds and reconciliation.
* Verify provider webhooks server-side, validate signatures, deduplicate events and reconcile amount/currency/reference.
* Never trust client-supplied amount or payment status.
4.8 Communication
* Target announcements to school, class, staff, parents or individual recipients by permission.
* Use Resend for email and Inngest for scheduled/retryable jobs.
* Track delivery attempts and failures; avoid sensitive information in email subjects.
4.9 Files and exports
* Keep Supabase Storage objects private and serve short-lived signed URLs after authorization.
* Validate file type, size, ownership and safe filenames.
* Run large exports asynchronously and apply tenant filters identical to the UI.
4.10 SaaS subscriptions
* Manage plan catalog, trials, entitlements, provider references and lifecycle.
* Enforce feature/usage limits server-side.
* Keep platform subscription billing separate from school fee collection.
5. Architecture and source structure
Use a modular monolith. Separate domain modules at the code boundary, share one deployment and Supabase Database database, and extract services only when workload or team boundaries justify it.
Tenant isolation requirements
Supabase Row-Level Security (RLS) is a core requirement. Enable RLS on every exposed tenant-owned table. Policies should use auth.uid() and verify an active SchoolMembership for the row's schoolId. Never trust a schoolId supplied by the browser on its own.
The service-role key bypasses RLS. Use it only in tightly controlled server-side administrative jobs and never expose it to the browser. Prefer user-scoped Supabase clients so policies are enforced by the database.
* Model School/Tenant and SchoolMembership explicitly.
* Every tenant-owned entity carries schoolId/tenantId or has a verified parent relation.
* Resolve active school on the server from a verified membership; never trust a browser-supplied tenant ID alone.
* Centralize tenant-aware data access and permission checks.
* Use compound unique constraints for school-scoped identifiers, e.g. (schoolId, studentNumber).
* Test cross-tenant denial for reads, writes, exports, file access, jobs and webhooks.
* Consider Supabase Database Row-Level Security only as defense in depth with carefully tested session context.

Server-side request flow
1. Authenticate the user with Supabase Auth.
2. Resolve the requested school and verify active membership.
3. Authorize the action using RBAC and resource-level policy.
4. Validate input with Zod on the server.
5. Execute domain logic; use transactions for coupled state changes.
6. Write audit events for sensitive actions.
7. Return only permitted fields and safe error messages.
6. Authentication, authorization and security
Supabase Auth strategy
Supabase Auth establishes sign-in/session integration but does not implement the complete school permission model. Select a currently supported adapter/configuration after checking version and deployment compatibility. OAuth providers are optional. For password login, use reputable password hashing, rate limits, safe recovery and session invalidation. For magic links, protect expiry and replay.
* Use HTTPS and secure HttpOnly/SameSite cookies in production.
* Keep session claims minimal and re-check fresh membership/permissions for sensitive actions.
* Rate-limit login, recovery, invitation and public endpoints.
* Protect recovery and invitation flows against enumeration and token reuse.
* Consider re-authentication or stronger controls for highly privileged operations.
Custom RBAC
students.read          students.create       students.update
attendance.take        attendance.correct
assessments.enter      results.approve       results.publish
fees.invoice           payments.reconcile    reports.export
staff.manage           school.settings.manage
platform.tenants.manage
Authorization decision = authenticated identity + active school membership + permission + resource scope + record-state policy. A teacher may enter marks only for assigned classes/subjects and within the permitted grading window.
Security baseline
* Validate all external input on the server; use parameterized database access.
* Apply appropriate CSRF/origin protections and safe security headers for the chosen request/session pattern.
* Verify webhook signatures using the provider's documented raw-body requirements.
* Keep secrets server-side; use least-privilege IAM and private Supabase Storage buckets.
* Scrub PII, tokens and payment data from logs, Sentry and analytics.
* Audit grade publication, attendance corrections, financial adjustments, role changes, exports and privileged support access.
* Define retention, deletion, backups, restore tests and incident response for target markets.
* Run dependency/secret scans and periodically review access.
7. Database model
This is a logical model; refine types, nullability, deletion behavior, indexes and constraints in Supabase JS. Use opaque IDs, explicit timestamps and database constraints for important invariants.

Database rules
Supabase-specific migration workflow: keep tables, constraints, indexes, triggers, functions and RLS policies in version-controlled SQL migrations under supabase/migrations. Use the Supabase CLI for local development and separate Supabase projects for development, staging and production.
Generate TypeScript database types from the Supabase schema and use them with the client. Use SQL functions/RPC for multi-step operations that must be atomic; make payment webhook handling and attendance writes idempotent.
* Use foreign keys and deliberate onDelete rules; preserve financial/academic history.
* Index common tenant and reporting filters (schoolId, studentId, classGroupId, status, createdAt) as appropriate.
* Use database functions/RPC for coupled workflows such as invoice creation and allocations so related changes are atomic.
* Use integer minor units or Decimal for money, never binary floating point.
* Store timestamps in UTC and render in the school's configured timezone.
* Use archive/status fields when records must remain auditable.
* Version migrations in source control and test them before production.
8. Core workflows
Admissions to enrollment
8. Registrar creates an application and adds required documents.
9. Application is reviewed and status changes are recorded with actor/time.
10. On acceptance, create student and enrollment in a transaction; prevent duplicate conversion.
11. Assign academic year, class and school-unique student number.
12. Notify guardians without exposing sensitive documents.
Attendance
13. Teacher opens an assigned class and selects an allowed session/date.
14. System loads roster and existing attendance.
15. Server verifies assignment, date rules and valid statuses.
16. Constraint/idempotency prevents duplicate session records.
17. Corrections require permission and reason; audit old/new values.
18. Optional background summary/guardian notification runs safely.
Assessments and report cards
19. Admin configures grading scale and weights.
20. Teacher enters scores; server validates range, assignment and grading window.
21. Teacher submits marks for review; authorized approver approves.
22. Authorized user publishes results; parent/student access follows publication policy.
23. Generate large report-card batches asynchronously and record artifact/version metadata.
Fee payment
24. Create invoice and line items with server-calculated amounts.
25. Create pending payment attempt with internal reference and provider metadata.
26. Initiate provider payment from the server.
27. Receive webhook; verify signature, deduplicate event and validate reference/amount/currency.
28. Update payment/allocation transactionally; browser redirect is not proof of payment.
29. Reconcile settlements and handle failures, reversals and refunds explicitly.
30. Generate a receipt only when the configured success state is confirmed.

10. UI/UX and accessibility
* Use consistent role-based navigation and a clear active-school indicator.
* Build mobile-first layouts; provide usable alternatives for wide data tables.
* Include loading, empty, error, success and permission-denied states.
* Use semantic headings, labels, keyboard navigation, visible focus and adequate contrast.
* Confirm sensitive/destructive actions and request reasons when appropriate.
* Support search, filters, sorting, server pagination and bulk actions for large lists.
* Provide printable receipts and report cards.
* Avoid fetching every student into the browser; paginate on the server.
* Use optimistic updates only with clear rollback behavior.
* Configure language, currency, date format and timezone per school.

* School A cannot read, edit, export or download School B records, even using guessed IDs or manipulated URLs.
* Every privileged server action verifies identity, membership, permission and resource scope.
* Enrollment and finance preserve integrity and audit history.
* Webhook processing is verified, idempotent and reconciled against amount, currency and reference.
* All forms validate on the server and errors do not leak internals.
* Core happy paths and denial paths are covered by automated tests.
* Lint, typecheck, tests, migration checks and production build pass in CI.
* Logs/analytics contain no passwords, tokens, full payment credentials or unnecessary student PII.
